Why is this host slow?

A PowerShell module that samples a Windows host and names the likely cause: a handle leak, sockets stuck in TIME_WAIT or CLOSE_WAIT, a CPU or memory squeeze, a deep disk queue. It exits non-zero on a critical finding, so a pipeline or a monitor can use it.

Source on GitHub

Real output

Run on the sample files in the repo (samples/). The samples are synthetic.

$ ./bin/slowhost.ps1 -SampleFile samples/handle-leak.json
host win-app-07  cpu 46.5%  mem 5200/16384 MB free  disk queue 0.3
CRITICAL HandleLeakSuspect  orders-api (pid 4120) holds 63211 handles
WARNING  TimeWaitPileUp     6400 sockets in TIME_WAIT (ephemeral port exhaustion risk)
exit 2

$ ./bin/slowhost.ps1 -SampleFile samples/cpu-starved.json
host win-app-03  cpu 98.2%  mem 600/8192 MB free  disk queue 6.5
CRITICAL CpuSaturated       CPU at 98.2%
CRITICAL MemoryPressure     7.3% memory available
WARNING  ThreadCountHigh    worker (pid 910) has 2600 threads
WARNING  CloseWaitPileUp    740 sockets in CLOSE_WAIT (an app is not closing connections)
CRITICAL DiskQueue          disk queue length 6.5
exit 2

$ ./bin/slowhost.ps1 -SampleFile samples/healthy.json
host win-app-01  cpu 22%  mem 9000/16384 MB free  disk queue 0.1
no findings
exit 0

Run it

git clone https://github.com/gerardrecinto/windows-slowness-triage
cd windows-slowness-triage
./bin/slowhost.ps1            # this machine, about 2 seconds

How it is checked

CheckWhat it does
Pester on Windows and LinuxRules are tested against sample hosts. The Windows-only collector test runs on a Windows runner.
PSScriptAnalyzerLint must be clean on every push.
SonarQube gateCommunity does not analyze PowerShell, so analyzer results are imported as external issues next to the Python findings, and the build waits for the quality gate.
GitLab CIThe same checks in .gitlab-ci.yml. The Windows job needs a runner tagged windows and has not run on one.
